# Userside -> PostGIS

Синхронизатор подготавливает неизменяемые версии данных для FastAPI.
Источник читается в REPEATABLE READ / READ ONLY, данные выгружаются серверными
курсорами порциями. На источнике ничего не создается и не изменяется.

## Запуск в Docker

Для запуска всей разработанной части в Docker (FastAPI + PostGIS + миграции +
импорт) см. [инструкцию запуска](../docs/docker-deploy.md).
Локально и на сервере используется один `compose.yml` и корневой `.env`.

Добавьте в `.env` параметры из `.env.example`, затем:

```sh
docker compose up -d --build --wait
docker compose run --rm jobs sync
```

API слушает `127.0.0.1:8000`. Миграции выполняются автоматически, PostGIS
доступна внутри Docker-сети, данные сохраняются в volume.

## Прямой запуск Python

Из корня проекта установите зависимости:

```sh
uv sync --project backend --locked
```

В существующий `.env` добавьте параметры нашей отдельной БД по `.env.example`.
US_DB_* используются только синхронизатором. MAP_DB_URL нужен для миграций
и записи результатов. Секреты не передаются аргументами команд.

## FastAPI для карты

После публикации набора запустите API:

```sh
uv run --project backend map-api
```

По умолчанию он слушает `127.0.0.1:8000`. Для отдельной ограниченной роли
задайте `MAP_API_DATABASE_URL`; при локальной разработке API также может
использовать `MAP_DB_URL`. API не читает параметры US_DB_* и не подключается к
Userside. Контракт запросов, ответы, лимиты и grants описаны в
[`docs/map-api.md`](../docs/map-api.md).

Проверки API без БД запускаются вместе с модульными тестами. Для интеграционных
тестов задайте `TEST_MAP_DB_URL` на отдельную PostGIS; тесты создают и удаляют
временные исходные базы.

Этот вариант требует доступной с хоста PostGIS и настроенного `MAP_DB_URL`.
БД стандартного Compose-стека не публикует порт на хост; для повседневной
разработки используйте команды Docker выше.

```sh
uv run --project backend map-db migrate
uv run --project backend map-db sync
```

Значение пароля в MAP_DB_URL должно быть URL-encoded, если содержит специальные символы.
Существующий `.env` скрипты не изменяют.

Для другого файла конфигурации:

```sh
uv run --project backend map-db --env-file /path/to/config.env sync
```

Миграции применяются транзакционно под advisory lock. Повторный запуск ничего
не меняет; изменение уже примененного SQL обнаруживается по контрольной сумме.
Запись в БД, содержащую таблицы Userside, запрещена и для миграций, и для импорта.

## Что переносится

| Слой | Записи | Геометрия |
| --- | --- | --- |
| Узлы связи | pbl_uzel, node_type_id=4 | Point, включая наследование от родителя |
| Муфты | pbl_uzel, node_type_id=1 | Point, включая наследование от родителя |
| Отдельные кабели | pbl_optica без принадлежности к трассе | LineString из концов и выбранного источника маршрута |
| Кабельные трассы | pbl_optica_mag + pbl_optica_mag_inc | MultiLineString всех уникальных кабельных участков |

Типы и скрытые/планируемые признаки сохраняются. Слои доступа оператора не
импортируются как права доступа: приложение получает полный набор исходных
картографических объектов, а затем фильтрует по слоям, zoom и видимости.
Тематические слои и связи меток сохраняются отдельно.

Опоры, колодцы, здания и промежуточные объекты используются как зависимости,
даже когда не имеют собственного видимого слоя в нашем приложении.
Сведения о клиентах ограничены ID и ID здания, и читаются только для концов трасс.
Пароли, платежи и другие клиентские поля не выгружаются.

Сборка маршрута сохраняет legacy-приоритет: заданные точки, промежуточные объекты,
канализация, прямая линия. Точки карт-планов исключаются. При равных position
исходный ID задает устойчивый порядок. Последовательные одинаковые вершины
убираются; циклы координат, недостающие зависимости, нулевая линия и поврежденные
координаты регистрируются как ошибки, а не маскируются прямой линией.

US_COORD_AXES задает порядок осей исходной geometry, по умолчанию lat_lon.
Точки pbl_optica_house читаются как x1=longitude, y1=latitude. Строковые координаты
legacy-трасс и дополнительных объектов читаются как latitude,longitude.
Исходные geometry с SRID, отличным от 0/4326, требуют отдельного адаптера.
POLYGON узла преобразуется по первой вершине, здание по центру bounding box.
Целевая geometry всегда 4326 и longitude,latitude.

Географическая длина и zoom повторяют стандартный расчет legacy: сферическое
расстояние с округлением вверх каждого сегмента. Учетные длины хранятся отдельно.
Пользовательская PHP-функция customRecalcMinFiberZoom в просмотренных исходниках
не найдена; переносится стандартная таблица порогов.

Стили кабелей учитывают тип, магистральность, число волокон, планирование,
метки и индивидуальный цвет. Стили точек содержат форму, цвета, порядок и
идентификатор иконки. Бинарные изображения этим этапом не копируются: sourceIcon
и sourceMarkerId сохраняются для будущего модуля локальных ресурсов.

## Ошибки и публикация

В Compose используется `SYNC_INVALID_OBJECTS=skip`: ошибочные объекты
исключаются, корректные объекты публикуются. Сведения об исключениях остаются
в `map_data.sync_issues` и отчётах, число — в `stats.excludedObjects`.
Неизвестный или поврежденный глобальный справочник блокирует весь запуск.
Пустой snapshot также не публикуется.

Вызов `map-db sync` вне Compose без переменной `SYNC_INVALID_OBJECTS` остаётся
строгим. Явная политика исключения для такого вызова:

```sh
uv run --project backend map-db sync --invalid-objects skip
```

Если после проверки журнала принято решение допустить конкретное количество
пропусков, это можно задать явно:

```sh
uv run --project backend map-db sync --invalid-objects fail --max-errors 10
```

Этот пример допускает максимум десять объектов с ошибками. Порог и количество
ошибок сохраняются в версии/журнале; пропущенные объекты не попадают на карту.
Пустой набор не публикуется даже при разрешенных ошибках.

Для просмотра результата в целевой БД:

```sql
SELECT id, status, started_at, finished_at, stats, error_code
FROM map_data.sync_runs ORDER BY started_at DESC;
SELECT source_kind, source_id, code, detail
FROM map_data.sync_issues WHERE run_id = :run_id ORDER BY id;
```

Один запуск на source_system/map_id защищен advisory lock. Новый запуск отмечает
прерванный предыдущий запуск. Опубликованные features/layers/links неизменяемы;
текущая версия переключается одной транзакцией. Отсутствие удаленной записи
в новом полном снимке естественным образом удаляет объект из актуального набора.

Завершенная версия включает все видимые данные; staging после успеха удаляется.
При неудаче staging сохраняется для диагностики. Загрузка исходника не требует
хранить сеть в памяти: зависимости читаются из целевого staging с ограниченными
кэшами. Частично собранные данные недоступны через active_datasets.

## Очистка и загрузки карты

```sh
uv run --project backend map-db cleanup --keep 2
# или для стека в Compose:
docker compose --profile tools run --rm jobs cleanup --keep 2
```

Хранятся минимум две последние версии каждого статуса для источника/карты.
Активная версия и версии с действующими query_leases не удаляются.
Логи sync_runs/sync_issues сохраняются после удаления версии.
Истекшие query leases удаляет эта команда. API выставляет им срок жизни согласно
`MAP_API_TTL_SECONDS` (по умолчанию 600 секунд), но не запускает отдельный цикл
очистки истекших строк. Пример ежедневного задания cron из корня репозитория:

```cron
25 * * * * /srv/userside-map/deploy/cleanup-map-leases.sh
```

Скрипт использует Compose-профиль `tools` и корневой `.env`; по умолчанию он
оставляет две версии снимка. Чтобы изменить их число, задайте планировщику
переменную `MAP_DATASET_KEEP`.

Preload в одной транзакции читает active_datasets под
`SELECT ... FOR SHARE`, создавать query_leases и фиксировать состав батчей.
Так очистка не сможет удалить версию между чтением указателя и созданием lease.
После истечения TTL батч должен возвращать ошибку истекшего запроса. Данные
старого набора могут закончить загрузку во время публикации следующего.

## Проверки

```sh
uv run --project backend pytest backend/tests/test_geometry.py
uv run --project backend ruff check backend
```

Для интеграционных тестов установите TEST_MAP_DB_URL на отдельную тестовую
PostGIS. Пользователь тестовой БД должен иметь CREATEDB: тесты создают и удаляют
собственные миниатюрные БД-источники. Не используйте рабочую БД для этих тестов.

```sh
uv run --project backend pytest backend/tests
```

Интеграционные сценарии: миграции и повторный запуск, исходник read-only,
полный импорт, удаление объекта, сбой проверки без переключения версии,
явно разрешенные ошибки, защита опубликованных объектов, взаимное исключение
запусков и удержание версии активной загрузкой. Без TEST_MAP_DB_URL эти тесты
явно пропускаются; модульные тесты выполняются независимо от PostgreSQL.

Проверено 2026-10-04: 31 тест прошел на отдельном PostgreSQL 16 / PostGIS 3.5,
SQL-миграции применяются повторно без изменений, wheel и sdist собираются.
Отдельный тест с двумя соединениями подтверждает, что публикация дожидается
завершения записей объектов; после публикации новые записи запрещены.
После восстановления доступа выполнен полный импорт реальной БД в отдельную
тестовую PostGIS: 3671 кабель, 1289 узлов и 2434 муфты, около 34 секунд.
Явный тестовый `--max-errors 163` разрешил пропуски: 84 точки без координат,
46 точек с недопустимой долготой, 23 кабеля без координат и 10 нулевых линий.
Все опубликованные геометрии валидны, SRID 4326. Повторный строгий импорт
заблокировал публикацию и сохранил предыдущую версию. Порог по умолчанию
не изменен; перед рабочим импортом требуется решение по этим исходным данным.
Подробности проверки исходной схемы, осей и импорта находятся в `docs/source-db.md`.

## Кабельные трассы как единый объект

Начиная с правил `userside-geographic-v3-cable-group-repair` объединения FiberMag
публикуются как `cable_group:<code>` в слое `cable_line`. Кабели-члены
отдельно не дублируются; кабель может участвовать в нескольких исходных трассах.
Пустое объединение не создаёт объект. Все участки собираются по обычным
правилам независимо от типов их концов и сохраняются в MultiLineString.
Разрывы не заполняются соединительными линиями. Повторные связи удаляются.

Пересечение bbox любым участком выбирает трассу целиком. Длина и zoom
рассчитываются по сумме участков, тематические слои объединяются. Для видимости
достаточно одного нескрытого участка с включённым в источнике типом; API
проверяет разрешённые типы по любому такому участку. В ответе остаются все
участки, включая скрытые и участки другого типа. Полностью скрытая трасса
не отображается. Единый стиль берётся у видимого участка с наименьшим ID.
В деталях доступны состав, концы участков и суммарные длины.

Ошибки геометрии участков обрабатываются по `US_CABLE_GROUP_ERROR_POLICY`
в `.env` и записываются как предупреждения, не расходуя `--max-errors`.
Миграция 006 допускает MultiLineString, не меняя существующие версии. Чтобы обновить карту, нужны миграция и новый полный импорт:

```sh
uv run --project backend map-db migrate
uv run --project backend map-db sync
```

В Docker обновите образ приложения, выполните `migrate`, затем `jobs sync`
и перезапустите API с новым образом. При смене версии клиент загружает трассы
с новыми ID; старые кабельные участки не смешиваются с ними.

### Два режима обработки ошибочных участков

```dotenv
# Вариант 1, по умолчанию: заменять ошибочные цепочки прямыми.
US_CABLE_GROUP_ERROR_POLICY=bridge
# Вариант 2: оставлять только корректные участки.
# US_CABLE_GROUP_ERROR_POLICY=drop
```

`bridge` использует связи концов кабелей (`uzelcode1`, `uzelcode2`,
`building2_id`), а не сортировку ID и не близость координат. Когда собственные
концы ошибочного участка известны, он заменяется прямой между ними. Несколько
последовательных ошибочных участков заменяются одной прямой между известными
объектами по обе стороны цепочки. Направление записи кабеля не влияет на обход.
Корректные геометрии не изменяются; разрывы между независимыми участками не
соединяются. При отсутствии двух разных известных координат, неизвестном
ветвлении или отсутствующей записи кабеля восстановить путь нельзя: соответствующие
участки пропускаются с предупреждением. Одинаковые координаты не образуют линию.

`drop` не добавляет прямых: публикуется MultiLineString корректных участков.
В обоих режимах трасса без единого пригодного участка не создаёт объект карты,
и это регистрируется предупреждением. Исходные ошибки сохраняются в журнале
даже после успешного восстановления. Ошибки иных объектов и справочников
сохраняют общую политику публикации и могут блокировать запуск.

В деталях трассы доступны `errorPolicy`, `geometryComplete`,
`reconstructedMemberIds`, `droppedMemberIds`, `bridges` и статус каждого члена
(`original`, `reconstructed`, `dropped`). Суммарная географическая длина и zoom
учитывают только опубликованную геометрию, включая восстановленные прямые;
учётная и оптическая длины сохраняют значения всех доступных исходных записей.
`memberIds` и ссылки сохраняют исходный состав, включая пропущенные участки.
Параметр также сохраняется в `datasets.config.cableGroupErrorPolicy`.

Настройка действует при следующей синхронизации, а не при каждом API-запросе.
Compose передаёт её сервису `jobs`; исходная БД не изменяется. Изменение `.env`
само по себе не пересобирает ранее опубликованную версию карты.

## Отчёты об объектах с ошибками

Каждый завершившийся запуск `sync` сохраняет `sync-<runId>.json` и
`sync-<runId>.md` в `SYNC_REPORT_DIR` (по умолчанию `reports/sync`). Отчёт
создаётся и при отказе публикации; запуск без проблем получает пустой список.
Пути выводятся в событии `issue_report` при отказе либо в результате успешного
запуска (`reports`). Файлы записываются в UTF-8 через временный файл и атомарную
замену, поэтому незавершённая запись не подменяет готовый отчёт.

Для каждой ошибки или предупреждения сохраняются:

- `type`, `id` — исходный тип объекта и ID;
- `name`, `description` — название и описание;
- `code`, `reason` — код и причина;
- `severity` — ошибка или предупреждение;
- `group_id` — трасса, если проблема относится к её кабельному участку.

Для кабеля название формируется из названий объектов его концов, описание
берётся из `pbl_optica.opis`. Для объектов `pbl_uzel` используются `nazv` и
`opis`. Для трассы используется `nazv`; если в источнике описание отсутствует,
поле остаётся пустым. При отсутствующей записи используется название с ID.
Один участок нескольких трасс может иметь отдельную запись для каждой трассы.
Сохраняются также предупреждения об участках, восстановленных режимом bridge.

Миграция 007 добавляет поля в `sync_issues`: информация сохраняется в момент
регистрации ошибки и остаётся доступной после очистки staging/datasets.
Старые записи журнала сохраняют ID и причины, но их названия и описания
автоматически не восстанавливаются, если исходный снимок уже удалён.

Настройка `.env`:

```dotenv
SYNC_REPORT_DIR=./reports/sync
```

В Docker каталог с хоста подключается к `jobs` как `/reports`, поэтому файлы
остаются после `docker compose run --rm jobs sync`. Создайте каталог заранее
и задайте `SYNC_REPORT_UID`/`SYNC_REPORT_GID` равными UID/GID его владельца
(`id -u`, `id -g`). В текущем локальном `.env` эти значения уже настроены.
Контейнер использует эти UID/GID для записи отчётов.

Повторный экспорт сохранённого запуска:

```sh
uv run --project backend map-db report <runId>
# Docker:
docker compose run --rm jobs report <runId>
```

Экспорт не требует подключения к Userside. Если файловая запись не удалась,
команда сообщает об этом явно; диагностические записи остаются в БД.
Если набор уже опубликован, ошибка сохранения файла не отменяет публикацию
и не меняет статус успешного запуска на failed.

## Кабельные тайлы

Vector/raster workers, ручная публикация и rollback, отдельные роли, Redis,
метрики и подключение внешней GIS описаны в
[эксплуатационном гайде](../docs/cable-tiles-operations.md).

Полное обновление: `docker compose --profile tools run --rm update-worker`.
Перед первым запуском: `docker compose --profile tools build update-worker`.
Worker выполняет sync → vector → raster → publish обоих форматов; UUID
подставляются автоматически. Python на хосте не требуется. Журнал продолжения
и отчёты sync хранятся в volume `map_updates` (`/updates/latest.json`).
Для cron используйте `run --rm -T`; пример в `docs/cable-tiles-operations.md`.

В Compose `SYNC_INVALID_OBJECTS=skip` по умолчанию: некорректные объекты
исключаются с отчётом, корректные данные проходят в новый snapshot и тайлы.
Пустой snapshot и ошибки всего импорта блокируют публикацию. Для строгой
проверки используйте `SYNC_INVALID_OBJECTS=fail` или `--invalid-objects fail`.

В Compose тайлы хранятся в SeaweedFS через S3 (`./tiles/seaweedfs`),
