# Пошаговый план реализации frontend

Дата: 2026-10-05. Статус: выполнен; результаты отмечены по фактическим проверкам.
Текущие результаты и ограничения ведутся в
[`frontend-validation.md`](frontend-validation.md).
Основание: [архитектура](architecture.md) и [согласованные требования этапа](frontend-phase.md).
Этот документ задает порядок работ, результаты и проверки; контракты и правила
обновления выборки определены в frontend-phase.md.

## Порядок и контрольные точки

1–3: подготовлены данные, границы модулей и запускаемое приложение.
4–6: первый сквозной результат — три типа объектов на спутниковой карте и детали по клику.
7–8: корректная работа при движении, ошибках, смене версии и истечении запросов.
9–10: инструменты, стили и законченный простой интерфейс.
11–12: шаблон адаптера, эксплуатационная документация и приемка.

Шаги выполняются последовательно; проверки каждого шага входят в его результат.
Проблемы реального импорта не мешают разработке на контролируемых тестовых данных,
но не позволяют объявить реальную интеграцию и итоговую приемку завершенными.

Начальная структура файлов (создается по мере реализации, не все сразу):

```text
frontend/
  app/                         приложение: страница, панели, карточка
  modules/
    map-data/
      module.ts                интеграция загрузчика с Nuxt
      runtime/core/            HTTP-клиент, очередь, объекты, версии, TTL
    cartography/
      module.ts                интеграция картографии с Nuxt
      runtime/core/            контракты, контроллер, реестры, инструменты
      runtime/adapters/maplibre/ движок, события, GeoJSON, перевод стилей
      runtime/components/      клиентский компонент карты
  tests/                       проверки ядра и браузерные сценарии
  templates/                   заготовка адаптера, появляется на шаге 11
  nuxt.config.ts
  package.json
  Dockerfile
```

Это модули внутри одного frontend-проекта. Отдельные публикации npm-пакетов
и универсальный менеджер плагинов для этого этапа не требуются.

**Результат:** определены владельцы состояния и направления зависимостей.
**Проверка:** контроллер связывается с тестовыми зависимостями без DOM/WebGL;
конфигурация не допускает включения неподдерживаемого типа или режима.

Фактические ограничения текущей приемки: визуальное сравнение стилей сделано на
контрольной выборке. Полный клиентский набор был загружен синтетическим preload
всей bbox при неподвижной демонстрационной камере; отдельный рендерный benchmark
подтвердил MapLibre idle для видимого viewport после приема всей выборки, но не
одновременную отрисовку всей сети в одном кадре. Повторяемый Chrome CDP benchmark на реальном опубликованном снимке фиксирует
первый отображенный batch, MapLibre `idle` при загруженных source/tiles, видимые
ID, WebGL upload/draw и process RSS. При полном мировом preload подтвержден idle
кадра viewport после приема всех batch; географически удаленные объекты не могут
одновременно отображаться в этом кадре. RSS/heap дают агрегатную оценку браузера,
не раздельные allocations MapLibre, WebGL и очередей. Все функциональные критерии
этапа пройдены; количественные ограничения и границы визуальной проверки перечислены
в отчете приемки.

**Результат — контрольная точка D:** этап принят по наблюдаемым результатам,
а не только по наличию компонентов. Результаты серверного бенчмарка не подменяют
проверку браузера. Отчет приемки: `docs/frontend-validation.md`.

## Что не расширяем в ходе этого плана

Первый этап использует существующий GeoJSON API, один адаптер MapLibre и одну
спутниковую подложку. Векторные тайлы сетевых объектов, другие движки, копирование
всех legacy-иконок и автоматическая область сети — отдельные последующие работы,
если они потребуются по измерениям или новой задаче. Критичные для согласованной
корректности дефекты текущего API устраняются в рамках соответствующего шага.
