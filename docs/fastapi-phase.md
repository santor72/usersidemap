# Фаза FastAPI: план разработки

## Цель и границы

Создать API, которое читает готовые объекты из нашей PostGIS и поддерживает
двухфазную прогрессивную загрузку карты. API не подключается к Userside,
не пересобирает маршруты и не изменяет опубликованные объекты.

В этой фазе: кабели, узлы связи, муфты, тематические фильтры, детали объектов,
фиксация версии и батчей, ограничения ресурсов, тесты и измерения.
Nuxt, TypeScript-загрузчик, отрисовка, перенос файлов иконок, авторизация
и инкрементальная синхронизация остаются отдельными фазами.

Исходная база для разработки уже есть: три SQL-миграции, синхронизатор,
пространственный индекс и тестовый снимок 7394 объектов. Его 163 пропуска
документированы в `source-db.md`; они не означают разрешение пропусков
для рабочего импорта. Существующая строгая политика не меняется.

## 1. Зафиксировать контракт

Создать `docs/map-api.md` с примерами запросов, ответов и ошибок.

| Endpoint | Назначение |
| --- | --- |
| `GET /api/map/layers?mapId=3` | Доступные типы и тематические слои текущей версии |
| `POST /api/map/objects/preload` | Фиксация выборки, версии и состава батчей |
| `POST /api/map/objects/batch` | Один батч GeoJSON из зафиксированной выборки |
| `GET /api/map/objects/{sourceKind}/{sourceId}?queryId=...` | Детали объекта из удерживаемой версии |
| `GET /health/live` | Процесс работает |
| `GET /health/ready` | Целевая БД и требуемая схема доступны |

Preload принимает `mapId`, `bbox=[west,south,east,north]`, целочисленный `zoom`,
`objectTypes` и необязательные `layerIds`. Источник задается конфигурацией
сервера, а не произвольным параметром подключения клиента.

Правила первой версии:

- Типы: `cable_line`, `node`, `coupler`; неизвестные типы отклоняются.
- Пустой список типов означает пустую выборку, а не все объекты.
- Координаты конечны и находятся в географических пределах; south < north.
- Bbox через антимеридиан поддерживается двумя областями без дублей.
- Только `hidden=false` и `min_zoom <= zoom`; планируемые объекты включены.
- Пустой или отсутствующий `layerIds` не ограничивает тематические слои.
- Непустой `layerIds`: объект входит хотя бы в один выбранный слой; без дублей.
- Кабель выбирается по пересечению всей линии с bbox, а не по концам.
- Полная геометрия выбранного объекта возвращается без обрезки и упрощения.

Preload возвращает `queryId`, `datasetVersion`, `expiresAt`, `totalObjects`,
счетчики по типам и список батчей: индекс с нуля, число объектов и вершин,
признак превышения мягкого бюджета одиночным тяжелым объектом.
Геометрии, большие свойства и исходные ID всех объектов в preload не передаются.
Пустая выборка возвращает ноль батчей.

Batch принимает только `queryId` и `batchIndex`, без повторной передачи bbox
и фильтров. Ответ содержит версию, индекс, число объектов и FeatureCollection.
Feature имеет стабильный ключ источника, тип, геометрию и компактный стиль.
Детали и ссылки на концы кабеля загружаются отдельным endpoint.
Детали доступны для объекта, входящего в данную зафиксированную выборку.

Прогресс считается по уникальным завершенным индексам и числу объектов,
а не по количеству HTTP-попыток или графических элементов отрисовки.

Ошибки получают общий формат с машинным `code` и безопасным сообщением:
422 для некорректных параметров, 404 для неизвестного запроса/батча/объекта,
410 для еще хранящегося, но истекшего запроса, 503 при недоступной БД
или отсутствии опубликованной версии. После очистки истекший queryId
неотличим от неизвестного и возвращает 404; клиент в обоих случаях повторяет preload.
Превышение лимитов получает отдельный код, без частичной успешной выборки.

Результат этапа: согласованный контракт, пригодный для независимой разработки клиента.

## 2. Каркас приложения и доступ к БД

Создать отдельный пакет `backend/map_api`, не смешивая HTTP-код с `map_sync`.
Структура: приложение, настройки, HTTP-схемы, endpoints, сервис загрузки,
репозитории PostGIS, реестр провайдеров и упаковка батчей.

Добавить FastAPI, ASGI-сервер, Pydantic и асинхронный psycopg pool;
обновить lock-файл и состав wheel. Пул запускается и закрывается через lifespan.
Обработчики не выполняют синхронные SQL-вызовы в event loop.

Разделить конфигурации: API использует только целевую БД, не требует US_DB_*.
У API отдельная роль с SELECT опубликованных данных и правами работы с таблицами
запросов. Миграции, публикация и административная очистка выполняются другой ролью.
Нужные grants оформить отдельной миграцией/документированной настройкой роли,
не выдавая API права владельца схемы.

Настроить размеры пула, ожидание соединения, SQL/lock timeout, TTL, лимиты
выборки и CORS allowlist. До появления авторизации запускать локально или
в доверенной сети, не публиковать открытый сервис в Интернет.
Секреты и полные строки подключения не попадают в ответы и логи.

Результат этапа: запускаемое приложение, health endpoints, HTTP-тесты lifespan.

## 3. Пространственная выборка и провайдеры

Реализовать реестр провайдеров для трех типов. Провайдер описывает поддерживаемый
тип, ограничения видимости и состав компактных свойств/деталей.
SQL-фрагменты определяются серверным кодом; значения передаются параметрами.
Добавление нового типа не должно требовать менять протокол preload/batch.

Репозиторий выбирает одну версию и применяет типы, zoom, видимость,
тематические условия и пространственное пересечение. Для тематических связей
использовать EXISTS или эквивалентную выборку без размножения строк.
Проверить EXPLAIN (ANALYZE, BUFFERS) для малой области и всей сети.

Preload читает только исходные ключи, типы и vertex_count; не считывает геометрию.
Порядок детерминированный: source_kind, source_id. Метаданные читаются порциями;
состав всей сети не накапливается списком в памяти Python.

Результат этапа: проверенные SQL-выборки, включая линию с обоими концами вне bbox.

## 4. Manifest, preload и жизненный цикл

Добавить новую миграцию после существующих, не редактируя примененные SQL.
Использовать `query_leases` для версии, нормализованных фильтров и фиксированного TTL.
Добавить реляционные `query_batches` и `query_items`: состав пачек, порядок,
исходные ключи и счетчики. Большие списки ID не дублировать в JSONB `batches`;
назначение существующего поля и его компактный формат явно документировать.

Индексы и ограничения должны обеспечивать уникальность объекта в запросе,
быстрое чтение по queryId/batchIndex, согласованность dataset_id и каскадное
удаление manifest при удалении lease. Все состояния доступны нескольким
процессам API; память процесса не является хранилищем queryId.

Preload выполняется одной ограниченной по времени транзакцией:

1. Прочитать `active_datasets` под `FOR SHARE` и удерживать блокировку до commit.
2. Создать lease на эту версию.
3. Выбрать метаданные, порционно построить и сохранить состав батчей.
4. Проверить лимиты, сохранить счетчики и срок действия.
5. Зафиксировать транзакцию и только затем вернуть manifest клиенту.

Ошибка или превышение лимитов откатывает весь запрос: частичного manifest нет.
TTL отсчитывается от завершения подготовки; повторные batch-запросы его не продлевают.
Для TTL использовать фактическое время БД (`clock_timestamp()`), а не время
начала транзакции; лимиты выборки проверять при порционном чтении и прекращать
подготовку сразу после превышения, не дочитывая неограниченный набор.
Проверить взаимодействие с уже реализованными публикацией и cleanup,
включая их порядок блокировок и отсутствие deadlock.

Начальные настройки для измерений, не окончательные эксплуатационные нормы:
100 объектов или 5000 вершин на обычный батч, TTL 10 минут,
до 100000 объектов и 2000000 вершин на запрос. Все значения серверные.
Один объект сверх мягких 5000 вершин получает отдельный батч.
Начальный жесткий предел объекта: 100000 вершин; превышение отклоняет preload
с явным кодом OBJECT_TOO_LARGE. Объекты не теряются и не режутся молча.

Результат этапа: стабильные пачки, общий для workers queryId, предсказуемое потребление памяти.

## 5. Batch, детали и защита загрузки

Batch в короткой транзакции блокирует lease под `FOR SHARE`, проверяет срок
по времени БД после получения блокировки и читает только свой query_items.
Блокировка сохраняется до чтения всех необходимых данных и защищает запрос
от одновременной очистки. После чтения данные сериализуются из ограниченного батча.
Очистка не может удалить используемую версию во время SQL-чтения.

Геометрию получать как GeoJSON из PostGIS. Упорядочивать ответ по manifest.
Повторный запрос одного батча возвращает те же объекты и версию; сервер
не хранит глобальную отметку "батч уже выдан" и не препятствует retry.
Публикация нового dataset не изменяет существующие запросы.

Детали используют ту же защиту lease и его datasetVersion. Передавать название,
сохраненные свойства, учетные и географические длины, связи и тематические слои,
не обращаясь к исходной системе.

Отмена HTTP-запроса и SQL-timeout освобождают транзакцию и соединение.
Периодическая очистка запускается одной административной задачей,
не отдельным независимым таймером в каждом worker.

Результат этапа: рабочая двухфазная загрузка и детали одной неизменяемой версии.

## 6. Проверки, измерения и приемка

Модульные проверки: упаковка по двум бюджетам, тяжелый одиночный объект,
пустой набор, устойчивый порядок, формат ошибок и валидация параметров.

HTTP + настоящая PostGIS: все три типа, границы геометрии, антимеридиан,
zoom, hidden/planned, тематические фильтры без дублей, повтор батча,
неизвестные ID, истекший lease, отсутствие текущего снимка и недоступность БД.

Конкурентные сценарии на разных соединениях/экземплярах приложения:
публикация во время preload, публикация между батчами, cleanup во время batch,
истечение срока при ожидании блокировки и retry на другом worker.
Проверить права роли API: запись в features/datasets и публикация запрещены.

На реальном тестовом снимке измерить preload, первый batch и полную загрузку,
SQL, размеры ответа до/после сжатия, пиковую память и поведение при параллельных
клиентах. Зафиксировать среду, количество объектов/вершин и p50/p95;
целевые latency и окончательные лимиты назначить по первому замеру,
не объявлять ускорение без измерений. Нагрузку проводить на нашей БД.

Проверить существующие тесты синхронизации, применение новых миграций
к чистой и уже созданной БД, повторное применение, lint и сборку пакета.
Документировать запуск API, настройки, очистку и примеры HTTP-запросов.

Фаза принимается, когда публичный контракт описан и проверен, API работает
без доступа к Userside, выборки корректны, батчи детерминированы и ограничены,
смена версии/очистка не ломает активную загрузку, нет скрытой потери объектов,
а все проверки и реальные измерения зафиксированы.

Следующая фаза: независимый TypeScript-загрузчик и Nuxt-карта с немедленной
отрисовкой каждого батча, отменой устаревших загрузок и ограниченной памятью.
Согласованные контроллер карты, независимый адаптер MapLibre, спутниковая Esri
и правила обновления выборки описаны в [frontend-phase.md](frontend-phase.md).
Сначала реализуется сквозной сценарий до деталей объекта, затем инструменты
и шаблон адаптера, выделенный из проверенной реализации.
