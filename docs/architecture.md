# План карты и синхронизации

Принято 2026-10-03, уточнено 2026-10-04 после принятия архитектурного ревью
frontend. Этот документ фиксирует актуальные решения; `plan00.txt` содержит
ранний вариант архитектуры.

## Поток данных

БД Userside -> модуль синхронизации -> наша PostgreSQL/PostGIS -> FastAPI -> карта.

FastAPI не обращается к исходной БД. Учетные данные источника доступны только
модулю синхронизации. Исходная БД используется для чтения.

Первая версия отображает кабели, узлы связи и муфты. Узлы и муфты читаются из
одной таблицы, но имеют независимые переключатели, статистику и правила слоя.
Загрузчик пишется независимым TypeScript-модулем для подключения к Vue/Nuxt.
Первый картографический модуль — MapLibre с одной спутниковой тайловой подложкой Esri.
Модуль данных, картография и frontend-приложение имеют отдельные публичные
интерфейсы. Картография состоит из общего контроллера и адаптера движка.
Приложение определяет доступные типы объектов и инструменты. Шаблон следующих
адаптеров выделяется после проверки работающей реализации MapLibre.
Согласованный следующий этап: [frontend-phase.md](frontend-phase.md).
Пошаговая реализация: [frontend-implementation-plan.md](frontend-implementation-plan.md).

## Архитектура frontend

```text
Nuxt-приложение: конфигурация, панели, карточка
                        |
                  MapController
                   /         \
          MapDataClient     MapLibreAdapter
               |                |
            FastAPI        карта и инструменты
```

MapDataClient владеет HTTP-протоколом, каталогом, поколениями запросов,
datasetVersion/queryId, очередью батчей, деталями и каноническими объектами.
MapController владеет конфигурацией и текущими фильтрами, связывает viewport
с загрузкой, управляет выбором и режимами инструментов. Адаптер отображает
изменения и сообщает о взаимодействиях; он не выполняет HTTP-запросы к API.

Приложение использует единый публичный интерфейс контроллера и не импортирует
MapLibre. Контроллер и загрузчик — независимые TypeScript-ядра с тонкой
Nuxt-интеграцией. Каталог доступен до создания WebGL-карты. Состояние изолировано
по экземплярам; геометрия и движок не входят в глубоко реактивное глобальное
хранилище. Между загрузчиком и адаптером передаются изменения объектов:
добавление, обновление, удаление и сброс с контекстом поколения.

Конфигурация различает `objectTypes` (типы объектов), `thematicLayerIds`
(фильтры Userside) и `basemap` (подложка). Поле `layers` для типов больше
не используется в публичной конфигурации frontend; HTTP-поле `layerIds`
сохраняется и заполняется клиентом данных из `thematicLayerIds`.
Верхние `objectTypes`/`tools` задают разрешенные возможности приложения,
`initialState` — первоначально включенные типы, фильтры и режим. Последующие
изменения выполняются командами контроллера. `select` и `measure` — режимы,
`zoom` — команда. Начальная область задается приложением через `initialView`.

Реестр типов задает имена для UI и обработчики. Каталог API сообщает о данных,
адаптер — о поддерживаемых типах, приложение — о доступном наборе.
Тематическая группа не требует отдельного обработчика; один тип может
отображаться несколькими внутренними слоями движка.

Первая реализация включает спутниковую Esri, выбор объекта, измерение расстояния
и управление масштабом. Преобразователь стилей явно переводит стиль backend
в оформление MapLibre; неперенесенные иконки имеют запасной символ.
Подложка настраивается отдельно, ее недоступность не блокирует API-загрузку.

Небольшой контракт адаптера определяется перед реализацией; шаблон и инструкции
расширения оформляются после сквозного сценария и проверки инструментов.
Второй полноценный движок и универсальный фреймворк плагинов для этого не нужны.
Nuxt добавляется в общий `compose.yml`, настройки задаются корневым `.env`.

## Правила переноса

| Наш тип | Источник | Условие / связи |
| --- | --- | --- |
| `node` | `userside3.pbl_uzel` | `node_type_id = 4` |
| `coupler` | `userside3.pbl_uzel` | `node_type_id = 1` |
| `cable_line` (отдельный кабель) | `userside3.pbl_optica` | Без членства в FiberMag; концы — объекты общей `pbl_uzel` или `building2_id` |
| `cable_line` (трасса) | `pbl_optica_mag`, `pbl_optica_mag_inc` | Один `cable_group`, MultiLineString всех уникальных `volscode`; выборка и подсветка целиком |
| Типы точек | `userside3.pbl_node_type` | Названия и JSON `style` |
| Типы кабелей | `userside3.pbl_cable_line_type` | Видимость и оформление |
| Тематические слои | `pbl_conf_layer`, `pbl_conf_layer_object`, `pbl_mark_object` | Отдельны от типа объекта |

Идентичность объекта: `(source_system, source_kind, source_id)`.
Для узлов и муфт `source_kind = node`; отображаемый тип не меняет идентичность.
При изменении `node_type_id` объект сохраняет исходный ключ.

Геометрия узла берется из `coord`; при отсутствии используется родительский
узел `parentuzel`. Цикл наследования или отсутствие координат записываются
в журнал как ошибка объекта. Опоры и колодцы могут потребоваться для сборки
кабелей, даже если их слои не отображаются.

Сборка кабеля сохраняет порядок из `Fiber::getLineCoordById()`:

1. Начальный узел.
2. Точки `pbl_optica_house`, упорядоченные по `position`.
3. Если заданных точек нет, промежуточные объекты `pbl_obj_int`.
4. Если предыдущие источники отсутствуют, трассы через
   `pbl_cable_duct_content -> pbl_cable_duct -> pbl_cable_route`, с учетом
   `position` и `direction`.
5. Конечный узел или центр здания.

Для географической карты учитывается legacy-правило исключения точек карт-планов.
Планы помещений не входят в первый этап. Карта источника по умолчанию имеет ID 3;
ее фактический тип требуется проверить перед импортом.

Нормализованная геометрия: SRID 4326, порядок `[longitude, latitude]`.
Исходный SRID и порядок осей проверяются по данным: PHP меняет порядок компонент.
Географическая длина для zoom рассчитывается отдельно от учетной длины кабеля.
Правило минимального zoom переносится из `recalcMinFiberZoom`, для точек
исходный порог равен 15. Стили переносятся с учетом типа, планирования,
магистральности, меток и индивидуальных переопределений.

## Логическая схема нашей БД

Структура реализована в `backend/map_sync/migrations/`. Команды применения,
синхронизации и очистки описаны в `backend/README.md`.

| Сущность | Назначение и основные поля |
| --- | --- |
| `sync_runs` | Запуск, начало/конец, статус, версия правил, счетчики и ошибка |
| `datasets` | Неизменяемая опубликованная версия, источник, карта, запуск |
| `active_datasets` | Указатель текущей версии для карты |
| `features` | Версия, исходный ключ, наш тип, название, геометрия, min_zoom, hidden, planned, style, properties |
| `feature_links` | Версия, кабель, роль endpoint, исходный ключ узла/муфты/здания |
| `layers` | Версия, исходный ключ слоя, название и параметры |
| `feature_layers` | Принадлежность объекта тематическому слою в версии |
| `sync_issues` | Запуск, исходный ключ, этап, код и описание проблемы |
| `source_records` | Временный согласованный снимок источника для сборки зависимостей |
| `query_leases` | Версия и срок удержания двухфазной загрузки |

`features` имеет уникальность по версии и исходному ключу. Пространственный
GiST-индекс и индексы версии/типа/слоя созданы миграциями.
Большие описания и зависимости не передаются в каждом батче; детали доступны
по отдельному запросу. Ссылки на изображения обслуживаются нашим backend;
файловые иконки при необходимости копируются отдельным модулем ресурсов.
Текущий синхронизатор сохраняет их исходные ключи, но не копирует файлы.

## Полная синхронизация и публикация

1. Один запуск для источника/карты получает согласованный снимок исходной БД.
2. Читает данные порциями, пакетно получает зависимости и строит новую версию
   в staging-таблицах. Сборка всей сети в памяти не требуется.
3. Проверяет геометрию, уникальность, связи и счетчики. Ошибки запуска и ошибки
   отдельных объектов различаются. Политика допустимых пропусков задается явно;
   первая версия по умолчанию не публикует набор с ошибками обязательных объектов.
4. В транзакции помечает подготовленную версию готовой и переключает указатель.
5. При сбое текущий набор остается доступным. Объекты, удаленные в источнике,
   отсутствуют в новой полной версии.

Старая версия удерживается для действующих queryId. Очистка удаляет только
неактивные версии без действующих загрузок; загрузки имеют ограниченный TTL.
Хранилище queryId общее для всех процессов FastAPI.
Инкрементальная синхронизация идет следующим этапом после изучения изменений
источника; она должна учитывать пересборку зависимых кабелей.

## Двухфазная загрузка карты

Двухфазная загрузка обязательна: данные тяжелые, каждый готовый батч отображается
до окончания остальных запросов.

- `POST /api/map/objects/preload`: карта, bbox, zoom, типы и тематические фильтры.
- Ответ: queryId, datasetVersion, totalObjects, описание пачек, expiresAt.
- `POST /api/map/objects/batch`: queryId и batchIndex.
- Ответ: версия, индекс, FeatureCollection и число обработанных объектов.
- Отдельный endpoint деталей использует исходный ключ и queryId, фиксирующий datasetVersion.

Preload фиксирует версию, фильтры и упорядоченный состав пачек после правил
видимости. Пустой набор возвращает ноль пачек. Батчи ограничиваются числом
объектов и бюджетом вершин; чрезмерно тяжелый отдельный объект обрабатывается
по явно заданной политике, без молчаливой потери.

Поскольку версия неизменяема, батчи не смешивают данные до и после синхронизации.
Для истекшего queryId backend возвращает явную ошибку, клиент повторяет preload.
Прогресс считается по завершенным уникальным пачкам и объектам, а не по числу
GeoJSON features: один объект может иметь дополнительные подписи.

Клиент ограничивает параллельность и повторы, инвалидирует поколение при начале
движения и отправляет новый preload после завершения движения/короткой задержки.
Нормализуются дробный zoom (floor в диапазоне 0–24), bbox и антимеридиан.
Поколение проверяется перед изменением хранилища и применением очереди отрисовки.

Preload не возвращает полный список ID. При перемещении с теми же фильтрами
и версией пересекающиеся объекты сохраняются до подтверждения новыми батчами;
заведомо вышедшие за область и отключенные типы удаляются раньше. После полного
успеха неподтвержденные объекты удаляются. При ошибке/отмене завершающая очистка
не выполняется как при успешной загрузке, неполный результат явно обозначается.
Число сохраненных кандидатов ограничено даже при последовательных отменах.

При смене API zoom текущие пересекающиеся объекты сохраняются до подтверждения
новой выборкой, затем неподтверждённые удаляются. Смена тематических фильтров
сбрасывает выборку: точную серверную фильтрацию клиент не повторяет. Неизменяемая
версия позволяет повторно подтверждать объект без замены геометрии в движке.
При обнаружении новой datasetVersion оставшаяся старая версия заменяется первым
принятым новым батчем, затем новая версия отображается постепенно. Пустой
успешный preload очищает карту. Разные версии не смешиваются; более строгий
сброс при смене карты/фильтров имеет приоритет перед сохранением старых данных.

Детали запрашиваются для объекта, подтвержденного в используемом queryId.
Истечение/очистка lease допускает один автоматический цикл восстановления
preload и повтор деталей после подтверждения. OBJECT_NOT_FOUND не считается
истечением lease. Смена выбора или версии инвалидирует старые ответы деталей.

История областей не накапливается; учет памяти включает GeoJSON движка и очередь
изменений. Обновления передаются порциями без пересборки всей коллекции на каждый
батч. Отмена браузерного запроса не гарантирует прекращения SQL-подготовки,
поэтому проверяется серверная нагрузка после отмен и настраивается очистка leases.

Выбор кабелей по пересечению готовой линии с bbox включит линии, чьи концы
находятся вне экрана. Это осознанное расширение legacy-выборки по концам.

## Этапы реализации и проверки

1. Проверить исходные типы колонок, SRID, порядок осей и конфигурацию карты 3.
2. Реализовать схему PostGIS и полный импорт узлов, муфт, кабелей и зависимостей.
3. Проверить совпадение координат, порядка маршрута, стилей и zoom с legacy.
4. Реализовать FastAPI preload/batch/details с версиями и ограниченным TTL.
5. Определить минимальные контракты контроллера, данных и адаптера; реализовать
   сквозной путь: каталог -> одна область -> батчи -> три типа -> выбор -> детали.
6. Проверить движение, фильтры, поколения, TTL, версии, ошибки и память.
7. Добавить инструменты и проверить стили; выделить шаблон адаптера из рабочей
   реализации, завершить Nuxt-интеграцию и общий Docker-запуск.
8. Измерить первую отрисовку, полную загрузку, SQL, объем передачи, отзывчивость
   и память на реальных данных; зафиксировать среду и ограничения.

Подробный план фазы FastAPI: [fastapi-phase.md](fastapi-phase.md).
Подробный план следующей фазы Nuxt и картографии: [frontend-phase.md](frontend-phase.md).

Обязательные сценарии: наследование/цикл координат, каждый источник маршрута,
обратное направление трассы, удаление объекта, сбой импорта, публикация во время
загрузки, устаревший ответ, retry без двойного прогресса и пустая выборка.
Индексы, детализация и размеры пачек настраиваются по измерениям.
Спутниковые тайлы подложки Esri входят в текущий frontend-этап.
