# Ревью архитектуры frontend

2026-10-04. Основание: согласованный [план](frontend-phase.md), фактический
`backend/map_api/app.py`, стили синхронизатора и замеры API.
Статус: принято пользователем 2026-10-04. Решения перенесены в
[основную архитектуру](architecture.md) и [план реализации](frontend-phase.md).
Реализация еще не начата. Текст ниже сохраняет обоснования ревью;
актуальные контракты и порядок работ определены в этих двух документах.
Спутниковая подложка Esri подтверждена пользователем и внесена в основной план.

## 1. Контроллер карты и адаптер движка

Разделение приложения, данных и картографии следует сохранить. Внутри
картографического модуля стоит различать контроллер и адаптер движка:

```text
Nuxt-приложение: конфигурация, панели, карточка
                   |
             MapController
              /         \
   MapDataClient       MapLibreAdapter
        |                  |
     FastAPI          карта и инструменты
```

Контроллер связывает viewport, фильтры, выбор и жизненный цикл загрузки.
Адаптер MapLibre получает изменения объектов и сообщает о взаимодействиях.
Он не выполняет preload и не знает HTTP-контракт backend. Замена адаптера
не требует переносить загрузку, обработку TTL и логику карточки.
Это внутреннее разделение одного модуля, не дополнительный сервис.

Публичный интерфейс остается единым для приложения. Каталог данных можно
получать через контроллер до создания WebGL-карты.

## 2. Шаблон без избыточной универсальности

Вначале нужны небольшой контракт адаптера и работающая реализация MapLibre.
После проверки трех слоев и инструментов из нее выделяется заготовка нового
адаптера. Полноценная система плагинов, базовый класс с наследованием и
попытка заранее абстрагировать все API нескольких движков пока не обоснованы.

Ядра данных и контроллера — обычный TypeScript; Nuxt-модуль регистрирует
компоненты, конфигурацию и composables. GeoJSON и экземпляр движка не должны
становиться глубоко реактивным глобальным состоянием приложения.

## 3. Три значения слова «слой»

В текущем предложении `layers` означает типы объектов, но backend возвращает
также тематические слои, а MapLibre имеет собственные слои отрисовки.
Принято использовать `objectTypes` для кабелей/узлов/муфт,
`thematicLayerIds` для фильтра Userside, `basemap` для подложки.
Один тип объекта может требовать нескольких слоев отрисовки: линия,
подпись, выделение, область попадания при клике.

Нужно различать разрешенные приложением типы и текущие включенные типы.
Аналогично разделяются доступные инструменты и активный режим взаимодействия.
`zoom` — постоянно доступная команда, а `select`/`measure` — режимы,
которые могут конкурировать за один клик.

Каталог API сейчас содержит ID типов, счетчики и min_zoom, но не полноценное
описание UI. Русские названия и оформление переключателей задает реестр типов.
API сообщает о наличии данных, адаптер — о поддержке, приложение — о доступности.
Ограничение в конфигурации UI само по себе не является серверной авторизацией.

## 4. Обновление выборки — главный риск корректности

Preload возвращает счетчики и описание батчей без полного списка ID.
Батч не передает min_zoom и тематические связи каждого объекта. Поэтому
клиент до получения всех батчей не может достоверно воспроизвести серверную
выборку после произвольной смены фильтров.

Принятая политика первой версии:

- При начале нового движения немедленно инвалидировать старое поколение;
  новый сетевой запрос отправлять после завершения движения/короткой задержки.
  Не запускать тяжелый preload на каждый кадр.
- При перемещении в рамках той же версии и тех же фильтров сохранять пересекающиеся
  объекты до подтверждения новым запросом. Каждый полученный объект помечать
  поколением; после успешного завершения удалить неподтвержденные объекты.
- Заведомо вышедшие за область объекты удалять раньше; проверка по оболочке
  допустима как предварительная консервативная очистка. Окончательный состав
  определяет backend. История областей не хранится.
- При смене zoom/тематических фильтров использовать сброс выборки как простой
  корректный вариант: данных для точной локальной фильтрации сейчас недостаточно.
  Отключенные типы скрывать и освобождать сразу.
- При смене datasetVersion заменять старую версию первым новым батчем и дальше
  отображать новую постепенно. Пустой успешный preload сразу очищает карту.
  Старую версию до замены обозначать как обновляемую, версии не смешивать.
- Ошибка/отмена не выполняет завершающую очистку как при полном успехе.
  Неполная загрузка и оставшиеся неподтвержденные объекты имеют явный статус.
  Ошибка при первом батче новой версии не превращает старые данные в актуальные.

Если эта политика дает заметное мерцание, следующим изменением может стать
добавление минимальных данных для локальной фильтрации в batch. Возвращать
огромный список ID в preload только ради плавности на первом этапе не нужно.

Отмена fetch не гарантирует прекращение подготовки manifest в БД. Нужны
объединение частых запросов и эксплуатационная очистка истекших leases.
Отдельно проверить отмену во время preload и реальную нагрузку после ухода клиента.

## 5. Передавать изменения, а не многократно пересобирать всю карту

Контракт между данными и отображением должен описывать добавление, обновление,
удаление и полный сброс. Не создавать отдельный MapLibre source/layer на каждый
объект и не пересылать весь растущий FeatureCollection после каждого батча.
Группировать источники по типам/потребностям отрисовки; объединять частые изменения.

В [текущем замере](map-api-benchmark.md) вся сеть — 7 386 объектов и 74 батча.
Этого достаточно для прямого GeoJSON-пути; собственное тайловое API на первом
этапе не требуется. Браузерная производительность этим замером не измерена.

MapLibre предоставляет обновления GeoJSON по изменениям при наличии стабильных
уникальных ID: [GeoJSONSource.updateData](https://maplibre.org/maplibre-gl-js/docs/API/classes/GeoJSONSource/).
Способ применения обновлений проверить на закрепленной версии библиотеки.

## 6. Детали объекта и границы API

Детали привязаны к queryId и его TTL. Пользователь может кликнуть по объекту
после десяти минут бездействия, когда геометрия еще показана, а lease истек.
Модуль данных должен ограниченно обновить preload и повторить детали, если
объект подтвержден в новом запросе. При смене версии/выбора запоздалые детали
отбрасываются. Продлевать lease постоянно фоновым таймером не требуется.

Не любой 404 означает истечение lease: `OBJECT_NOT_FOUND` и `BATCH_NOT_FOUND`
отличаются от `QUERY_NOT_FOUND`. Поведение определяется кодом ошибки API.

MapLibre может использовать дробный zoom и долготы за пределами стандартного
диапазона, а API принимает целый zoom 0–24 и нормализованный bbox.
Контроллер нормализует параметры; для текущего min_zoom подходит floor с
ограничением диапазона. Проверяются антимеридиан и обзор шире целого мира.
Начальные center/zoom или bounds задаются приложением: API сейчас не возвращает
область сети. Автоматический показ всей сети потребует отдельного поля каталога.

## 7. Подложка и стили

Выбрана спутниковая Esri. Конкретный способ подключения, атрибуция и параметры
доступа оформляются отдельной конфигурацией подложки; загрузка сетевых объектов
работает независимо от доступности тайлов.
Официальная [интеграция Esri с MapLibre](https://developers.arcgis.com/maplibre-gl-js/api-reference/BasemapStyle/)
поддерживает imagery и управление атрибуцией; конкретный endpoint будет выбран
при реализации без привязки интерфейса карты к этому SDK.

Стили backend не равны MapLibre paint/layout: например, dashArray приходит
строкой, формы точек и zIndex требуют перевода в правила движка. Нужен явный
адаптер стилей и запасные символы для еще не перенесенных иконок. Обещание полного
визуального совпадения с legacy допустимо только после такой проверки.

## Принятый порядок

Сначала реализовать один сквозной сценарий: каталог -> одна область -> батчи ->
три типа объектов -> клик -> детали. Затем проверить движение/отмену/память,
добавить инструменты и оформить шаблон адаптера. Так контракт выводится из
работающих сценариев и остается небольшим.
