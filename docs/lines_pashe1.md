# Логика сборки кабелей и загрузки на карту

Сейчас логика разделена на два этапа: сборка геометрии кабеля при синхронизации и загрузка готовой линии для текущего экрана карты. При перемещении карты кабель заново не собирается.

Общий путь:

```text
Userside → сборка кабеля → PostGIS → FastAPI → MapDataClient → MapLibre
```

## 1. Из чего собирается кабель

Для нас кабель — самостоятельный объект карты независимо от того, куда он проложен: между узлами связи, муфтами, столбами, до клиента или другого объекта. Типы конечных объектов нужны для получения координат и связей; они не должны ограничивать выборку кабелей. Отсутствие отдельного отображаемого слоя для конечного объекта также не должно исключать кабель.

Основная запись в рассматриваемом коде — `pbl_optica`. Поля `uzelcode1` и `uzelcode2` ссылаются на записи общей таблицы `pbl_uzel`, а не исключительно на узлы связи. Эта таблица содержит разные типы объектов, в том числе муфты. Альтернативный конец задаётся через `building2_id`.

Нельзя отождествлять исходный `source_kind = node` с отображаемым типом `object_type = node`: первый обозначает запись общей таблицы источника, второй — слой узлов связи. В текущем импорте узлы связи (`node_type_id = 4`) и муфты (`node_type_id = 1`) выделяются в самостоятельные объекты карты. Для сборки кабелей координаты читаются из общей таблицы без этого ограничения по типу, поэтому другие её объекты могут участвовать как концы или промежуточные точки кабеля.

Прямая ссылка на клиента не представлена среди импортируемых полей самой записи `pbl_optica`. При сборке зависимой трассы `pbl_cable_route` клиентский конец поддерживается: его координаты определяются через здание. Это описание текущей реализации, а не ограничение требования: кабели до клиентов и других объектов должны попадать на карту; полноту их представления в исходных данных нужно проверять по соответствующим связям.

Алгоритм находится в `backend/map_sync/geometry.py`, метод `GeometryBuilder.cable()`, и повторяет основную последовательность PHP `Fiber::getLineCoordById()` из `main/main/legacy/Fiber.php`.

```text
Начальный объект (узел связи, муфта, столб и т. д.)
     ↓
Один выбранный источник промежуточных точек
     ↓
Конечный объект или центр здания
```

Промежуточные точки выбираются по приоритету, а не объединяются из всех источников:

| Приоритет | Источник | Что добавляем |
|---|---|---|
| 1 | `pbl_optica_house` | Заданные координаты кабеля, исключая карты-планы |
| 2 | `pbl_obj_int` | Координаты промежуточных объектов общей таблицы `pbl_uzel` или координаты из JSON |
| 3 | `pbl_cable_duct_content → pbl_cable_duct → pbl_cable_route` | Геометрию трасс |
| 4 | Нет промежуточных записей | Прямую линию между концами |

Записи упорядочены по `position`/`pos`, при равенстве — по исходному ID. Для трассы с `direction > 0` порядок её точек разворачивается.

Особенность: наличие записей `pbl_obj_int` блокирует переход к трассам, даже если эти записи не добавили ни одной координаты. Это соответствует флагу `$isCustomCoord` в PHP.

## 2. Как обрабатываются координаты

Для объекта общей таблицы `pbl_uzel` (включая муфту, столб и другие типы) используются собственные координаты; при их отсутствии проверяется `parentuzel`. Циклы наследования считаются ошибкой. Название метода `GeometryBuilder.node()` здесь обозначает работу с общей таблицей источника, а не ограничение концов кабеля узлами связи.

Если указан `building2_id`, конец кабеля берётся из здания, даже при заполненном `uzelcode2`. Для полигона здания используется центр его ограничивающего прямоугольника.

Результат — `LineString` с координатами `[longitude, latitude]`. Соседние одинаковые точки удаляются. Если остаётся меньше двух точек, кабель считается ошибочным.

Здесь Python строже PHP: отсутствие обязательных координат вызывает ошибку объекта; PHP в ряде мест просто пропускает точку.

## 3. Что сохраняется после сборки

### Требование: кабельная трасса как единый объект

Если в исходной системе несколько кабельных участков объединены в кабельную трассу, для карты это единый логический кабель. Нужно сохранять и отображать геометрию всех его участков независимо от типов объектов на концах. Выбор и подсветка должны относиться ко всей трассе.

В изученном PHP есть объединение кабелей `FiberMag`: `pbl_optica_mag` содержит трассу, а `pbl_optica_mag_inc` связывает её `magcode` с отдельными кабелями `volscode`. Это отличается от `pbl_cable_route`, чья геометрия используется через каналы для сборки отдельного кабельного участка.

Реализовано: Python импортирует `pbl_optica_mag` и связи `magcode → volscode`. Трасса сохраняется как `source_kind = cable_group`, `object_type = cable_line`, ID на карте — `cable_group:<code>`. Её геометрия — `MultiLineString` из всех уникальных участков. Участки, входящие в трассу, отдельно не публикуются; кабели без трассы сохраняются обычными `LineString`. Пустые трассы не создают объект карты.

Сборка выполняется в `backend/map_sync/cable_groups.py`. `MultiLineString` сохраняет разрывы, ветвления и кольца без искусственных соединительных отрезков. Повторные связи с одним участком не дублируют его геометрию. Участки упорядочены по ID, что не требует предполагать линейную топологию трассы.

При загрузке по bbox пересечение любого участка выбирает единый объект трассы с геометрией всех участков. Zoom рассчитывается по сумме географических длин. Трасса видима, если хотя бы один участок не скрыт и его тип разрешён для карты; фильтр разрешённых `cableTypeId` также применяется по любому такому участку. Тематические слои объединяются из участков. После выбора объекта в ответ входят все его куски, включая скрытые или другого типа. Если все участки скрыты, трасса скрыта целиком.

Стиль трассы берётся у видимого участка с наименьшим ID; планируемой трасса считается, если планируемы все участки. В деталях доступны ID и свойства каждого участка, его концы, суммарные географическая, учётная и оптическая длины. Дополнительно сохраняются `errorPolicy`, `geometryComplete`, восстановленные и пропущенные ID, а также описание добавленных прямых. Географическая длина рассчитывается по опубликованной геометрии; учётные длины — по всем доступным исходным записям. Ошибки участков регистрируются как предупреждения и обрабатываются согласно `US_CABLE_GROUP_ERROR_POLICY` в `.env`: `bridge` (по умолчанию) восстанавливает ошибочный участок или цепочку прямой между известными концами по топологии; `drop` отбрасывает ошибочные участки. Геометрические ошибки членов трассы не блокируют публикацию. Если двух известных разных координат нет либо путь неоднозначен, даже в режиме `bridge` участок пропускается с предупреждением. Трасса без пригодных участков не создаётся. Ошибки других объектов по-прежнему подчиняются общей политике публикации.

MapLibre отображает все части с одним ID. Контроллер при клике по отрисованному фрагменту выбирает полную геометрию из MapDataClient. Для использования новой сборки нужно применить миграцию `006_cable_groups.sql` и выполнить новую синхронизацию.

В `backend/map_sync/sync.py`, функция `build_features()`, сохраняются геометрия, связи с концами кабеля, свойства и стиль. Поле `routeSource` показывает использованный источник: `places`, `objects`, `ducts` или `direct`.

По географической длине полученной линии рассчитывается минимальный zoom:

| Длина линии | Минимальный zoom |
|---|---:|
| < 50 м | 14 |
| < 100 м | 13 |
| < 250 м | 12 |
| < 500 м | 11 |
| < 1000 м | 10 |
| ≥ 1000 м | 1 |

Это длина геометрии, отдельно от учётной и оптической длины.

Оформление в `backend/map_sync/styles.py` учитывает тип кабеля, магистральность, число волокон, планирование, тематические слои и индивидуальный цвет.

## 4. Какие кабели FastAPI отдаёт карте

Preload в `backend/map_api/app.py` выбирает кабели опубликованной версии, удовлетворяющие условиям:

- включён тип `cable_line`;
- кабель не скрыт;
- `min_zoom ≤ zoom` запроса;
- готовая линия пересекает `bbox`;
- выполнены фильтры типа кабеля и тематических слоёв.

Типы начального и конечного объектов в этой выборке не фильтруются. Кабель между муфтами или с концом на столбе выбирается по тем же правилам, что и кабель между узлами связи. Отключённые слои конечных объектов не должны влиять на загрузку слоя кабелей.

Сейчас разрешённые `cableTypeId` по умолчанию — только `1`, через `MAP_API_VISIBLE_CABLE_TYPE_IDS`. Это дополнительный фильтр, помимо `is_on_map`.

Пересечение проверяется для всей линии: кабель попадёт в выборку и тогда, когда оба конца за экраном, но маршрут проходит через экран. Геометрия возвращается целиком, без обрезки по `bbox`.

## 5. Как линия появляется на карте

`MapDataClient` в `frontend/modules/map-data/runtime/core/client.ts` отправляет область, целочисленный zoom и фильтры в `/objects/preload`. Ответ фиксирует `queryId`, версию данных и список пачек.

Затем клиент загружает `/objects/batch`, по умолчанию до четырёх запросов одновременно. Каждый полученный кабель имеет стабильный ID `cable:<id>` и сразу передаётся на отрисовку.

Адаптер MapLibre в `frontend/modules/cartography/runtime/adapters/maplibre/adapter.ts` группирует изменения до ближайшего кадра и обновляет источник линий через `updateData`.

## 6. Что происходит при перемещении карты

В начале движения текущая загрузка отменяется. Через 180 мс после остановки запускается новая.

При перемещении и смене zoom с прежними фильтрами пересекающиеся объекты временно сохраняются. После успешной загрузки удаляются кабели, которые новая выборка не подтвердила. При ошибке завершающая очистка не выполняется. Старые ответы отсекаются по поколению запроса.

В исходном `main/main/js/getusdata.v3.js` тоже есть preload и пачки, но нет такой защиты от устаревших ответов, а уже загруженные объекты только пропускаются по ID. Кроме того, `batchSize = 3` фактически запускает два обработчика из-за условия `i < batchSize`.

Главные места для дальнейшего разбора — приоритет источников маршрута, поведение при неполных координатах и фильтр `cableTypeId`: именно они определяют, какую линию мы соберём и увидим ли её на карте.

Настройка текущего `.env`: `US_CABLE_GROUP_ERROR_POLICY=bridge`. Переключение на `drop` начинает действовать после новой синхронизации.

## Отчёт синхронизации об ошибках

Каждый запуск сохраняет JSON и Markdown в `SYNC_REPORT_DIR` (текущая настройка:
`reports/sync`). Отчёт содержит ID, название, описание и причину ошибки,
а также тип объекта, уровень (ошибка/предупреждение) и ID трассы для её участков.
Сохраняются как восстановленные, так и пропущенные проблемные участки.
Отчёт создаётся при успешном запуске и при отказе публикации. Запуск
без ошибок получает отчёт с пустым списком. Данные объектов сохраняются
миграцией 007 в `sync_issues` и не теряются при очистке временных снимков.
Повторный экспорт: `map-db report <runId>`.

Проверка на реальном источнике: отчёт запуска
`831576b6-fd8b-460d-ba45-290b73a1b844` содержит 150 ошибок и 18 предупреждений.
Файлы находятся в `reports/sync/`. Для Docker настроены постоянное подключение
каталога и UID/GID для записи. Рабочий опубликованный набор этой проверкой
не изменялся.

## Исправление отрисовки при смене zoom

Обычные кабели выводятся отдельным слоем без `line-dasharray`. Ранее запасной
шаблон `[1, 1000000]` создавал огромные пробелы и скрывал разные фрагменты
при изменении масштаба. Штриховые кабели используют отдельный слой с прежними
шаблонами; оба слоя принадлежат одному источнику и выбору объекта.
При смене zoom слой не очищается до загрузки: прежние пересекающиеся объекты
сохраняются до подтверждения, затем удаляются отсутствующие в новой выборке.
Повторное подтверждение объекта той же неизменяемой версии сохраняет ссылку
на геометрию и не вызывает повторную передачу объекта в MapLibre.
